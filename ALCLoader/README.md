# ALC Loader
This is an example module that uses the `ALC Loader` setup.
The `ALC Loader` example has two assemblies in the module:

+ `ALCLoader.dll`
  + Contains the cmdlets, any public types used by the cmdlets, and any dep references inside the ALC
+ `ALCLoader.Loader.dll`
  + Contains only the ALC setup code, it is loaded in the default ALC on PowerShell 7

Some pros and cons using this method over the [ALC Resolver](../ALCResolver/README.md) example are:

|Pros|Cons|
|-|-|
|Assembly deps can be used by the cmdlet directly|Requires an internal method to support force importing a module a 2nd time|
|No need for an OnImport or OnRemove to cleanup the ALC|Still requires a `.psm1` to load the assembly|
|Public types in the module assembly can be used as cmdlet parameters and outputs|Only one copy of the module can be loaded per process|
|The exact dependency is loaded, it won't use any existing loaded assemblies||

## Structure
The module consists of 3 components:

+ PowerShell module [ALCLoader.psd1](./module/ALCLoader.psd1) and [ALCLoader.psm1](./module/ALCLoader.psm1)
+ ALC loader assembly [ALCLoader.Loader](./src/ALCLoader.Loader/)
+ Binary module assembly [ALCLoader](./src/ALCLoader/)

The names of the C# projects used here don't have to be exactly the same, the key part is the `ALCLoader.Loader` contains the `AssemblyLoadContext` setup code and `ALCLoader` contains the cmdlets and code that calls the deps which are contained in the ALC.
The loader finds the module assembly by removing the `.Loader` suffix from its own assembly name.

When PowerShell loads `ALCLoader` it will run the code in [ALCLoader.psm1](./module/ALCLoader.psm1) which on PowerShell 7 will create the ALC.
This is done by calling [ALCLoader.Loader.LoadContext](./src/ALCLoader.Loader/LoadContext.cs) to create the ALC, load our binary module, and return the loaded assembly inside that ALC.
Finally the `psm1` will then load the assembly as normal and export the cmdlets within that assembly.

The loader assembly is loaded in the default ALC and stays loaded for the life of the process.
As assemblies cannot be unloaded, only one copy of the module can be loaded per process and the `psm1` will refuse to import a copy of the module from a different path.
Importing the same copy again with `-Force` will reuse the existing ALC.

## Dependency Resolution
The ALC uses [AssemblyDependencyResolver](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.loader.assemblydependencyresolver) with the `ALCLoader.deps.json` file generated by `dotnet publish` to find the module's dependencies.
This also supports RID specific managed and native assets under `bin/<tfm>/runtimes/` so keep the standard `dotnet publish` layout intact.

Only assemblies listed in `ALCLoader.deps.json` are loaded in the `ALCLoader` ALC.
Anything not listed falls back to the default ALC which is the copy shipped with PowerShell or .NET.
Whether a dependency is bundled is decided at build time by the `PackageReference` in [ALCLoader.csproj](./src/ALCLoader/ALCLoader.csproj):

+ To use PowerShell's copy, set `ExcludeAssets="runtime" PrivateAssets="all"` like `System.Management.Automation`
  + Only do this when every supported PowerShell version ships an assembly version at least as high as the one compiled against
+ To bundle a copy, use a plain `PackageReference`
  + Do not add `PrivateAssets="all"`, the SDK treats it as `Publish="false"` and the assembly is silently not published
+ An assembly that is part of the .NET shared framework is only published when the package version is higher than the runtime's
  + Otherwise build conflict resolution drops it and the runtime copy is used

Check `ALCLoader.deps.json` and `bin/<tfm>/` in the built module to confirm what was bundled.

## Public Types
PowerShell can resolve types defined in `ALCLoader.dll` by name because the module imports that assembly directly with `Import-Module -Assembly`.
This means public types defined in the module assembly itself can be used as cmdlet parameters and outputs, there is no need for a separate shared assembly to exchange types with the caller.

```csharp
namespace ALCLoader;

// Can be used as a parameter or output type and referenced
// in PowerShell as [ALCLoader.MyResult].
public sealed class MyResult
{
    // The dependency object is kept internally.
    internal YamlDotNet.Serialization.ISerializer Serializer { get; }

    // Exposed using built-in types only.
    public string Value { get; }
}
```

What PowerShell cannot resolve are types from the dependencies in the ALC, for example `[YamlDotNet.Serialization.Serializer]` and `'YamlDotNet.Serialization.Serializer' -as [type]` will fail.
Even if it could, the type could clash with a copy of the same assembly in the default ALC.
So:

+ Cmdlet parameter types must be either built-in types (BCL or `System.Management.Automation`) or types defined in `ALCLoader.dll` itself
  + Never use a dependency's type as a parameter type
+ Never write a dependency's object directly to the pipeline or expose one as a public property type
  + Wrap it in an `ALCLoader` type that exposes the needed data through built-in or `ALCLoader` types
  + The wrapper may keep the dependency object internally
